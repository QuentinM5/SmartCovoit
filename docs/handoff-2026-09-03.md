## Le projet

SmartCovoit est une appli de covoiturage pour événements ponctuels
(mariage, sortie de groupe, tournoi…) : un organisateur crée un événement
avec une adresse de rendez-vous et une date, partage le lien, chacun
s'inscrit comme conducteur ou passager pour l'aller, le retour, ou les
deux. Un solveur OR-Tools (VRP à capacité) calcule qui monte avec qui pour
minimiser la distance/durée totale. Après calcul, un glisser-déposer permet
de réorganiser manuellement (recalcul serveur par insertion la moins
chère).

- **Backend** : `backend/`, FastAPI + SQLAlchemy 2.0 async, migrations
  Alembic, Python 3.11.
- **Frontend** : `frontend/`, Next.js 16 (App Router) + Tailwind v4,
  déployé sur Cloudflare Workers via `@opennextjs/cloudflare`.
- **Base de données** : Postgres géré par Neon, **partagé** entre deux
  instances backend (voir déploiement).
- **Convention du code** : commentaires et messages en français,
  expliquant le *pourquoi* (pas le quoi), pas de commentaire redondant avec
  le code. Style déjà en place à respecter dans toute nouvelle contribution.

## Travail réalisé cette session (chronologique)

### 1. Revue à 5 agents du projet

Cinq relecteurs indépendants (pragmatique, avocat du diable, rigoureux,
premiers principes, généraliste) ont audité le code, se sont notés
mutuellement en aveugle, puis un agent président a tranché. Conclusion
principale : le code marche réellement (49 tests à l'époque, tous
vérifiés en exécution) mais tournait **sans authentification du tout** —
le trou le plus large et consensuel. Autres constats notables non encore
traités (voir "Dette connue" plus bas) : le Worker de failover peut
dupliquer des écritures (POST rejoués sans clé d'idempotence), pas de
plafond/rate-limit sur les inscriptions ni sur `/solve`, zéro test
frontend, zéro télémétrie produit.

### 2. Décisions produit (posées explicitement par l'utilisateur)

- **Positionnement : un vrai produit pour tout le monde**, pas un outil
  entre amis — ce qui rend l'authentification prioritaire (déjà fait, voir
  ci-dessous).
- **Triple infra (TrueNAS + Railway + Worker) : gardée telle quelle**,
  décision explicite — ne pas proposer de la simplifier sans qu'on le
  redemande.
- **Solveur VRP (OR-Tools) : gardé pour l'instant**, mais l'utilisateur
  veut qu'on valide un jour avec de vrais utilisateurs s'ils préfèrent
  choisir eux-mêmes qui va avec qui plutôt que le calcul automatique — à
  garder en tête, ne pas re-proposer de le retirer sans que ce retour
  existe.
- **Modèle aller/retour indépendant par personne : à valider** avec 2-3
  organisateurs réels avant de décider de le garder ou de le simplifier.

### 3. Authentification (comptes + Google) — fait, déployé, vérifié

- **Jeton JWT dans l'en-tête `Authorization: Bearer`, PAS de cookie** :
  décision technique déduite du fait que frontend et API sont sur des
  domaines différents (`qmeyer.fr` vs `workers.dev`) — un cookie de session
  y serait tiers et bloqué par défaut par Safari. Jeton stocké côté client
  dans `localStorage` (`frontend/lib/auth.ts`), 30 jours, pas de
  rafraîchissement automatique.
- **Connexion Google via Google Identity Services** (bouton officiel, pas
  le flux OAuth complet à redirection serveur) — évite un secret client à
  gérer, le frontend envoie directement un jeton d'identité déjà signé par
  Google à `POST /auth/google`, vérifié côté serveur.
- **Modèle `User`** : email/mot de passe et/ou Google (email = clé
  d'identité commune, rattachement automatique si un compte Google se
  connecte avec un email déjà utilisé par un compte mot de passe).
- **Comptatibilité historique** : `Event.owner_id` et
  `Driver.user_id`/`Passenger.user_id` sont nullables, **sans backfill**
  (aucun utilisateur réel n'existait pour les anciennes lignes). Règle
  d'autorisation : un événement/inscription sans propriétaire connu reste
  ouvert à n'importe quel compte connecté ; tout ce qui est créé après
  cette migration a systématiquement un propriétaire, donc protégé.
- **Matrice d'autorisation** (implémentée dans `backend/app/api/routes.py`,
  helpers `_check_owner_or_open` et `_can_remove_participant`) :
  organisateur seul pour calculer/réorganiser les trajets et changer
  l'image ; chacun peut retirer sa propre inscription ; l'organisateur peut
  retirer n'importe qui.
- **Corrections faites lors d'une relecture à froid** (avant déploiement) :
  faille de timing sur `/auth/login` (temps de réponse différent selon que
  l'email existe ou non → énumération de comptes, corrigé par une
  vérification bcrypt systématique contre un hash factice), race condition
  non gérée sur les inscriptions concurrentes (500 au lieu d'un 409 propre,
  corrigé avec un `except IntegrityError`), et un bug d'UI où la page
  affichait brièvement le mauvais état (formulaire au lieu de l'invite de
  connexion, ou l'inverse) pendant l'hydratation du jeton stocké.

### 4. Enrichissement des événements — fait, déployé, vérifié

- **Date d'événement** : obligatoire à la création, backfillée depuis
  `created_at` pour les événements historiques.
- **⚠️ Correction en cours de route** : une première version avait ajouté
  un **fil de commentaires multi-auteurs** (table `comments`, un auteur par
  commentaire) — c'était un malentendu. Le besoin réel est un **message
  unique de l'organisateur, saisi à la création** (`Event.description`,
  texte libre, pas de discussion). La table `comments` a été créée
  (migration `0004`) puis supprimée (migration `0005`) dans la même
  session — **si tu vois `comments` dans une vieille migration ou de la
  doc, c'est obsolète, ignore-le.**
- **Image de couverture** : stockée en base (`bytea` + `content_type`,
  colonne `deferred` pour ne jamais la charger sauf demande explicite via
  `GET /events/{id}/cover-image`) plutôt qu'un service de stockage objet
  dédié — décision volontaire pour ne pas ajouter une pièce d'infra de plus
  sur deux hôtes backend pour un usage aussi ponctuel. Affichée en vignette
  4:3 (`aspect-[4/3] w-28 sm:w-36`), pas en bannière pleine largeur.
- **Mini-carte du point de rendez-vous** (`frontend/components/location-map.tsx`,
  nouveau) : à côté du titre, juste un marqueur, pas les tournées — la
  carte complète (`RouteMap`) reste plus bas sur la page, une fois un
  calcul fait. Les styles clair/sombre de carte Google Maps ont été
  mutualisés dans `frontend/lib/google-maps.ts` (`MAP_LIGHT_STYLE`/
  `MAP_DARK_STYLE`, exportés) plutôt que dupliqués entre `RouteMap` et
  `LocationMap`.

   — l'utilisateur devait les ajouter via le dashboard (fichier
   `smartcovoit_railway_env_vars.txt` laissé sur son Bureau lors d'un tour

   `/solve` (coût CPU + appels Google Routes payants).

   session (vignettes, page login/signup, bouton Google en situation
   réelle).
5. **Tests frontend** : toujours zéro, alors que la logique la plus

6. **Télémétrie produit minimale** — aucune trace d'usage réel actuellement.
7. **Fonctionnalités évoquées avec l'utilisateur sans être lancées** :

## Comment reprendre

- Toujours lire `docs/deploiement.md` avant de déployer quoi que ce soit —
  il documente les pièges déjà rencontrés (CORS, build qui fige une
  mauvaise URL, etc.).
- SSH TrueNAS : nécessite un agent ssh-agent chargé avec la clé
  passphrase-protégée (`~/.ssh/agent.env` sur la machine de dev — `source`
  ce fichier avant tout `ssh`/`scp`). Si la connexion échoue, vérifier
  d'abord que l'utilisateur n'a pas désactivé Cloudflare WARP/One (c'est
  arrivé deux fois cette session) avant de creuser une autre piste.
- Toute migration Alembic touche la **vraie base de production partagée**
  — jamais de `alembic upgrade head` en local sans avoir conscience de ça.
  Une dry-run SQL (`alembic upgrade head --sql`) avant application réelle
  est la pratique déjà établie cette session, à garder.
- Le style du code (commentaires expliquant le *pourquoi*, français,
  patterns d'optimistic UI, etc.) est cohérent dans tout le repo — le lire
  avant d'ajouter du code plutôt que d'improviser un style différent.
